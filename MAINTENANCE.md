## 2. Basic Editing Workflow

The website is maintained locally using GitHub Desktop.

### Standard workflow

1. Open the local `lionrajmohan.github.io` folder.
2. Edit the required file.
3. Save the file.
4. Open GitHub Desktop.
5. Review the **Changes** tab.
6. Check the changed files.
7. Enter a meaningful commit message.
8. Commit the changes.
9. Push the changes to GitHub.
10. Wait for GitHub Pages deployment.
11. Open the live website and check the result.

### Important

Do not make simultaneous edits in the GitHub browser and the local GitHub Desktop copy unless necessary.

If GitHub Desktop shows **Pull origin**, pull first before making another change.

# 7. Research Themes

Research themes are stored in:

```text
data/research.yml
```

The homepage automatically reads this file.

### To add a new research theme

1. Open:

```text
data/research.yml
```

2. Copy an existing research-theme entry.
3. Change the name.
4. Change the research group if required.
5. Save the file.
6. Commit and push.

### Important

Do not manually create duplicate research-theme cards in `index.md` if the page already uses the YAML data.

The website should generate the cards automatically.

---

# 8. Publications

The publication system is intended to use structured data rather than repeatedly formatting HTML manually.

When `data/publications.yml` is created, publications should be added there.

### Recommended publication fields

```text
year
title
authors
journal
type
doi
publisher
theme
```

### Adding a publication

1. Copy an existing publication record.
2. Enter the bibliographic information.
3. Verify the title and journal.
4. Verify the DOI.
5. Select the correct publication type.
6. Assign the appropriate research theme.
7. Save.
8. Commit and push.

### Publication quality rule

Do not add an unverified DOI.

Do not invent bibliographic information.

Do not create duplicate publication records.

# 14. Website Statistics

Visitor statistics may eventually include:

* unique visitors
* page views
* cumulative visitors
* countries
* selected country flags

### Important distinction

Do not use a generic label such as:

```text
Visitors
```

when the underlying metric is actually page views.

Use accurate labels such as:

```text
Unique Visitors
Page Views
Countries Reached
```

Statistics should come from an appropriate analytics system.

The website should not attempt to identify individual visitors.

# 17. Content Accuracy

Permanent website information should be accurate and defensible.

Before publishing:

* verify dates
* verify designations
* verify publication information
* verify DOI
* verify project information
* verify institutional names
* verify external profile links
* distinguish current and historical information
* avoid unsupported rankings or claims

Where a number is still being reconciled, do not present it as a definitive permanent statistic.

---

# 18. Academic Evidence Principle

Where practical, important claims should lead to supporting information.

Examples:

```text
Publication → Publication record → DOI
Research project → Project details
Institutional affiliation → Official NITW profile
Scholar identity → Google Scholar / ORCID / Scopus
Event → Event record / photographs / video
Lecture → YouTube lecture
```

The website should function as a useful evidence and discovery layer rather than simply reproducing a CV.

---

# 19. Before Making Major Changes

For a major modification:

1. Identify the affected file.
2. Check whether the file is used elsewhere.
3. Make one logical change at a time.
4. Test the website.
5. Commit with a clear message.

Example commit messages:

```text
Add NITW academic identity links
Add publication data structure
Improve homepage statistics
Add event archive
Update research themes
```

Avoid vague messages such as:

```text
changes
update
new
```

---

# 20. If Something Breaks

First check:

1. The file path.
2. YAML indentation.
3. Missing quotation marks.
4. Missing closing HTML tags.
5. Incorrect Liquid syntax.
6. Incorrect image path.
7. Incorrect link.
8. GitHub Pages deployment status.

Do not make multiple unrelated changes while troubleshooting.

Return to the last known working version if necessary.

---

# 21. Golden Rule

**Content should be easy to update.
Design should be reusable.
Data should be structured.
Claims should be verifiable.
The website should remain maintainable without depending on the original developer.**
